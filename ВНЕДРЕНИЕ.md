# A-SERVICE · передача разработчикам

Исходный проект для внедрения на a-service.asia. Витрина соответствует версии 10, утверждённой заказчиком 24 ноября 2026 года. В этой редакции PDF отправляет менеджер вручную. Формы подключены к FastAPI, заявки и запросы материалов попадают в действующую CRM. В архиве лежат исходники, готовые страницы, админка Next.js и инструмент переноса изменений в вашу ветку.

## 1. Как перенести изменения в свою ветку

Создайте ветку от текущей рабочей ревизии и зафиксируйте в ней локальные изменения. Распакуйте этот ZIP рядом с рабочей копией. В терминале из **распакованной** папки выполните:

```sh
python release/apply_update.py --target "../my-working-copy" --check
python release/apply_update.py --target "../my-working-copy" --apply
```

Вместо `../my-working-copy` укажите папку исходного проекта, в которой лежат `admin`, `backend`, `frontend` и `src`. Для путей Windows можно указывать абсолютный путь в кавычках. Первая команда только проверяет файлы. Вторая переносит изменения, если файлы совпадают с исходным архивом или с обновлением. Локальные правки в затронутых файлах выводятся списком. При конфликте автоматический перенос останавливается до записи.

Для ветки, которая уже ушла вперёд, выполните трёхстороннее сравнение: базой служит прежний архив, второй версией — ваш текущий код, третьей — этот пакет. Используйте список изменённых файлов и их контрольные суммы из `release/changes.json`. Новые файлы, настройки среды и базы данных рабочего проекта, которых нет в списке, скрипт не трогает. Инструменты из папки `release` нужны только для переноса.

## 2. Где находятся изменения

| Задача | Файлы и интерфейсы |
|---|---|
| Главная, 11 страниц услуг и 10 кейсов на каждом языке | `src/bank_site/`, а также общие JS, CSS и медиа в `frontend/`. Опубликованные HTML собираются в `frontend/ru/` и `frontend/kk/`. |
| Одностраничная анкета и выбор услуги | `frontend/quote.js`, `frontend/quote.css` и `POST /api/requests`. Принимает телефон или email, код услуги, необязательный комментарий, язык и идентификатор отправки. |
| Запрос профиля компании | `frontend/material-request.js`, `POST /api/material-requests`. Имя, email, необязательный телефон и язык. PDF хранится под `backend/app/` вне публичной папки сайта. |
| Приём и хранение | `backend/app/routers/bank_requests.py`, `backend/app/services/bank_intake.py`, `backend/app/models/bank_request.py`. Обращение, запись в журнале и задания отправки сохраняются в одной транзакции. |
| Почта | `backend/app/services/request_mail.py`. Обе формы создают по одному служебному уведомлению ответственному. После запроса материалов менеджер сам связывается с заказчиком и отправляет профиль на языке заявки. |
| Работа менеджера | Существующий раздел «Заявки» в `admin/`. В карточке видны контакт, категория и состояние служебного уведомления. Для запроса профиля есть отдельный фильтр и скачивание PDF по языку заявки через авторизованный `GET /leads/{lead_id}/material`. Доступ к карточке и статусам требует обычной авторизации сотрудника. |
| SEO и старые адреса | `src/build.py`, `src/bank_storefront.py`, `src/redirects.txt`, `backend/app/static_site.py`. Собираются карта сайта, ссылки между языками, поиск и перенаправления. Прежние статьи, инструкции и городские страницы входят в общий сайт. |

Штатный `POST /public/leads` оставлен для расширенной заявки с приложениями. Номера и статусы прежних лидов сохраняются. Для новых обращений используется существующая таблица `leads` и добавляются две таблицы — `bank_requests` и `bank_request_mail`. Повтор с тем же `requestId` и теми же данными возвращает подтверждение одной заявки. В админке услуги, запросы PDF и старые заявки находятся в общем журнале.

На главной видны шесть основных услуг. Остальные пять доступны в разделе дополнительных работ. В портфолио все десять карточек одного размера. Внутри мобильной версии фото сохраняют пропорции, увеличиваются по нажатию, а в кейсе про отделку ниши пары кадров идут друг под другом. На страницах монтажа, перевозки и козырьков работают отдельные слайд-шоу. Первым в монтаже показывается жёлтый банкомат на стропах крана зимой.

## 3. Сборка и настройки

На тестовом контуре используйте копию базы и тестовый SMTP. Тестовая база с очередью писем должна отправлять только в локальный перехватчик почты. Настройки PostgreSQL, авторизации и контактов из действующего окружения храните отдельно от архива. Для пустой БД задайте `SEED_ADMIN_EMAIL`, `SEED_ADMIN_PASSWORD` (от 16 символов, до 72 байт UTF-8) и постоянный `SECRET_KEY`. Выполните `python -m app.seed` из `backend/`. При наличии пользователей seed сохраняет действующие учётные записи. После создания первого администратора можно удалить временные реквизиты SEED из окружения, сохранив `SECRET_KEY`.

| Настройка | Что указать |
|---|---|
| `DATABASE_URL` | На тесте — отдельная БД. При внедрении — существующая БД сайта с резервной копией. |
| `REQUESTS_NOTIFY_EMAIL` | Рабочий email сотрудника или отдела, принимающего заявки и запросы PDF. |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`, `SMTP_USE_TLS` | Настройки своего почтового сервера и разрешённого отправителя. Для новых писем с TLS порт 587 использует STARTTLS, 465 — прямой TLS. |
| `ASERVICE_SITE_URL`, `ASERVICE_INDEXABLE` | Полный адрес сайта. На тесте укажите адрес стенда и `0`, для выпуска на официальном домене — `https://a-service.asia` и `1`. |
| `ASERVICE_API_URL`, `CORS_ORIGINS` | В штатной схеме сайт и API на одном домене, `ASERVICE_API_URL` пустой. При разделении укажите API при сборке и добавьте точный HTTPS-адрес витрины в CORS backend. |
| `NEXT_PUBLIC_API_URL`, `ADMIN_URL` | Существующие адреса API для админки и самой админки. Для локального примера — `http://localhost:8000` и `http://localhost:3000`. |

Основной сервис Railway запускается из корня. Админка остаётся отдельным сервисом с корнем `admin/`. Для локального запуска используйте Python версии из `.python-version` и Node.js с npm для админки. Пример из корня (команды сервера и админки выполняются в разных терминалах):

```sh
python -m pip install -r requirements.txt
python src/build.py
cd backend
python -m app.seed
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Во втором терминале:

```sh
cd admin
npm ci
npm run build
npm start
```

После правки текстов и шаблонов витрины выполните из корня:

```sh
node src/bank_site/prerender.mjs
python src/build.py
python src/tools/check_discovery.py
```
 Обычный деплой использует уже подготовленные страницы, подготовка HTML в Node.js на хостинге не требуется. Настройки `ASERVICE_*` для статических страниц следует задавать до сборки. На Railway храните настройки в переменных сервисов. Локально параметры `SEED_ADMIN_*` также можно указать в `backend/.env` при запуске из `backend/`.

## 4. Приёмка перед выпуском

1. Сделайте резервную копию БД. Разверните тестовую ветку и запомните номер одной прежней заявки. После сборки и запуска откройте её снова и проверьте доступ к приложенному файлу, если он был.
2. Откройте страницу услуги на ширине телефона. Услуга уже выбрана. Введите тестовый контакт и отправьте. Должны появиться галочка и одна запись в «Заявках», ответственному должно прийти уведомление. При невалидном контакте форма показывает ошибку.
3. На русской и казахской главных страницах запросите профиль с разными тестовыми email. На экране должно появиться подтверждение приёма. В CRM должны появиться две заявки с соответствующими языками, в рабочем ящике менеджера — два уведомления со ссылками на карточки. Убедитесь, что тестовые ящики клиентов пусты. Скачайте из каждой карточки PDF, проверьте язык и отправьте один экземпляр вручную из тестового почтового ящика менеджера.
4. Проверьте журнал и уведомления после сбоя SMTP. Запись заявки остаётся в системе. Временно неотправленное письмо ждёт повтора. Если соединение оборвалось после передачи письма, проверьте журнал SMTP перед ручными действиями: сервер мог принять сообщение.
5. Проверьте `/health`, `/ru/`, `/kk/`, `/sitemap.xml`, `/robots.txt` и постоянный переход с прежней ссылки на услугу. На тесте запретите индексацию. До выпуска на основной домен сверьте адреса, получателя почты, формы и права сотрудника.

Автоматические тесты сервера запускаются из папки `backend` командой `python -m unittest discover -s tests -v`. Локальные тестовые запросы и письма не входят в архив.

## 5. Индексация после подключения домена

1. Соберите официальный сайт с `ASERVICE_SITE_URL=https://a-service.asia` и `ASERVICE_INDEXABLE=1`. На отдельном тестовом домене используйте адрес стенда и значение `0`. Проверьте, что на боевом домене сервер и CDN отдают страницы с кодом 200 и позволяют получать открытые тексты и фотографии без входа в аккаунт.
2. В HTML русской и казахской версии проверьте заголовок, описание, основной текст, канонический адрес, ссылки на языковую пару и JSON-LD. Для контрольной проверки подойдут `/ru/uslugi/montazh-i-demontazh-bankomatov/` и `/ru/proekty/perevozka-bankomatov/`. У старых закладок проверьте код 301 и конечный адрес.
3. После выпуска добавьте `https://a-service.asia/sitemap.xml` в подтверждённые кабинеты Google Search Console, Яндекс Вебмастера и Bing Webmaster Tools. Первой вручную проверьте главную, затем одну услугу и один кейс в обеих локалях. Если перед сайтом работает WAF, проверьте доступ поисковых краулеров и OAI-SearchBot по журналу запросов.
4. Оценивайте результат по факту обхода, индексации страниц, показам и переходам по услугам в Казахстане. Карту сайта и файлы `/llms.txt` и `/llms-full.txt` обновляет сборка. Положение в выдаче и выбор ссылок в ИИ-ответах зависят от внешних систем.

## 6. Выпуск и откат

После приёмки выпускайте основной сервис и админку из одной версии. Если уже развёрнута версия с автоматической отправкой клиенту, остановите все её процессы рассылки до переключения на новую версию. Запустите обновлённый сервер и проверьте старую очередь. Сверьте с журналом SMTP записи с неопределённым результатом, прежде чем отправлять материал вручную. При откате сохраните базу и новые обращения. Если откатываетесь на версию с автоматической отправкой PDF, оставьте её доступ к исходящему SMTP отключённым до восстановления ручного сценария.
